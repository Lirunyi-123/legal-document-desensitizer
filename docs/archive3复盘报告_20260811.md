# archive3 批量脱敏实战复盘报告

日期：2026-08-11

## 一、本轮实战目标

从公开渠道搜集各类法律文书（判决书、裁定书、调解书、起诉状、银行流水等），
优先 PDF 格式，完成 30+ 份文书的两阶段脱敏（规则层 + 语义层），每份文书
结果独立归档于 `archive3/<编号>_<名称>/`，并针对实战中发现的问题修复规则、
补充回归测试、更新 SKILL，最终推送 GitHub。

## 三、实战中发现并修复的问题（8 项）

### P1 微信号替换导致 SecureDesensitizer 崩溃（阻断级）
- 现象：处理第一份判决书即崩溃
  `TypeError: _safe_replace_wechat() takes from 2 to 4 positional arguments but 5 were given`。
- 根因：基类 `Desensitizer._safe_replace_wechat` 增加 `shift` 参数时，
  `SecureDesensitizer` 的覆写未同步更新。
- 修复：补上 `shift` 参数并透传。

### P2 扫描件 PDF 未自动路由到"原图涂黑"
- 现象：7 份扫描件 PDF 全部报
  "PDF 文本层找不到任何待脱敏内容…请先对 PDF 做 OCR"。
- 根因：`in_is_scanned_pdf` 仅在显式传 `--image-redact` 时检测；
  `-o out.pdf` 未触发扫描件检测，落到文本层涂黑分支。
- 修复：`-o .pdf` 时也自动检测文本层并路由到扫描件涂黑分支。

### P3 PDF 涂黑后文本层重排，语义层/还原配对失败
- 现象：最高法大 PDF（106/156 页）阶段二报
  `映射配对失败：[公司_1] 剩余阶段一 1 语义 0`；
  排查发现涂黑 PDF 文本层出现 `[当事人_5\n]`（占位符被折行）、
  `[当事人_5]` 出现次数与映射表不一致（159 vs 158）等重排伪影。
- 修复：
  1. `run_semantic_pass` 先做占位符空白归一化（`[当事人_5\n]` → `[当事人_5]`）；
  2. `mask --pdf-redact` 额外落一份"掩码文本侧车"（与映射表同源），
     阶段二直接读侧车，避免二次提取不一致；
  3. 扫描件分支侧车改为保存 `result.text`（此前误保存 `image_redact.py`
     返回的原始 OCR 文本，导致侧车无占位符）。
- 附带修复：`image_redact._redact_pages` 此前返回 `ocr_text`（未脱敏文本）
  却声明返回 `masked_text`，一并修正为返回 `result.text`。

### P4 常见词上下文被误判为人名（大量假阳性）
- 现象：最高法判决书把"用**于威某**EX5""相**关底盘**零部件"“**项目名**称”
  中"于威某/关底盘/车底盘/项目名"当人名涂黑，且涂黑后文本重排
  使这些值在 residual 校验中"复活"（实为假阳性残留）。
- 根因：
  1. 候选姓氏与前一字构成常见词（用于/相关/关于/有关…）未拦截；
  2. "相关"跨行成"相\n关底盘"时前一字回看没跳过空白；
  3. 技术/机构名词尾缀（底盘/技术/关系/零部件/人员…）未拦截；
  4. 3 字候选因列末空白/标点非法时 `break`，导致 2 字真名（"张伟 "→"张伟"）
     漏掉。
- 修复：新增 `_NAME_SURNAME_PREFIX_BLOCK`（跨空白回看）、
  `_NAME_SUFFIX_BLOCK`（技术名词尾缀/前缀），黑名单补充
  关于/相关/用于/关系/项目名/车底盘等；候选长度循环 `break` 改 `continue`。

### P5 英文为主的银行流水被过度涂黑
- 现象：涉外银行流水中 Banking/Limited/Business/Statement 等英文词全部
  被"独立微信号"规则替换（217 处 [微信号]），整份文档语义被破坏。
- 根因：独立微信号模式 `[a-zA-Z][a-zA-Z0-9_]{5,19}` 无法区分英文单词。
- 修复：
  1. 中文字符占比 <2% 的文档禁用独立微信号启发式；
  2. 独立微信号候选必须含数字/下划线（纯字母微信号走"微信号：xxx"上下文
     或语义层）。

### P6 银行流水交易行孤立姓名漏脱敏
- 现象：中文银行流水中"对方户名"列的单次出现姓名（王秀英/张伟/陈志强）
  未被掩码（裸人名启发式要求强上下文或频率≥2）。
- 修复：新增 `_in_txn_row`——行首含日期、候选后紧跟 8 位以上数字账号
  （或候选前为转账/代发/消费等摘要词）时视为交易行对方户名，放行掩码。

### P7 银行流水摘要被公司名规则吞掉
- 现象："代发工资 杭州云杉科技有限公司"被整体替换为 [公司_1]，
  摘要"代发工资"被误吞。
- 修复：`_COMPANY_LEAD_WORDS` 增加银行摘要词
  （代发工资/转账支出/转账收入/消费/转入/转出/利息/手续费等），
  修剪公司名匹配串时剥离摘要前缀。

### P8 模板类文书空映射导致阶段二报错
- 现象：官方起诉状模板（无实际敏感信息）阶段一映射表为空，
  阶段二报"未能从映射表解析出任何条目"。
- 处理：批量脚本识别该场景，标注"模板/无敏感信息"，跳过语义层并出说明。

## 四、OCR 环境排障记录（重要）

实战中扫描件 OCR 一度静默返回空、或报 `nilError`，排查结论：
- macOS Vision 框架在**沙箱内不可用**（返回 `nilError`），在非沙箱
  （escalated）环境下正常——工具本身无 bug，但文档已注明"OCR 需在
  非沙箱/本机环境运行"。
- `ocr_vision.swift` 改用 `VNImageRequestHandler(url:)` 优先加载图片，
  cgImage 路径失败时回退，增强对 PyMuPDF 抽取图片的兼容性。
- `_ensure_ocr_bin` 使用独立 clang 模块缓存目录、源码更新自动重编、
  编译后跑 `--selftest`（PIL+系统字体绘制 "ABC 123" 校验 OCR 输出），
  避免复用损坏的共享模块缓存导致"静默空"二进制。

## 五、验证结果

- 34 份文书全部完成两阶段脱敏（1 份模板类标注无敏感信息跳过语义层）。
- 新增 8 项 v4.1 回归测试，全量单测 170 项通过。
- 独立抽查 6 份脱敏 PDF：身份证/手机号样本 0 残留；
  扫描件为像素级涂黑（text 层近似为空，符合预期）；
  09/10 中的"残留"为专利号（2017203xxxx），非个人敏感信息。
- 每份文书均生成映射表（明文，附警告），可 `restore` 还原；
  PDF 掩码文本侧车保证还原校验与原文逐字节一致。

## 六、遗留限制与后续建议

1. 涉外/英文人名（Mei Ling Tsang 等）无中文姓氏形态，规则层不掩码；
   建议语义层/LLM 层补充或引入音译姓名规则。
2. 账户号带分隔符（9896-6767-3233）未被现有银行卡规则覆盖，
   建议新增"格式化解"（`\d{4}-\d{4}-\d{4}-\d{4}`）规则。
3. 纯字母微信号（无数字下划线）需靠上下文规则；语义层可兜底。
4. 中文银行流水真实扫描件无法公开获取（隐私），本轮以公开英文基准 +
   明确标注的合成中文样本补充，后续可接入律所内部已授权样本。
5. 维基共享资源的若干扫描 PDF（如 03/19）为低质或占位内容，已从
   最终语料剔除，保留真实可用样本。
